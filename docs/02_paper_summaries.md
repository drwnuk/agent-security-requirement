## P01 — 2026.emnlp-main.2233.pdf
- Title: Athena: Vulnerability-Affected Library Identification via Knowledge Graph Completion
- Venue: EMNLP 2026 (main)
- Authors: Trinh Duy, Dang Yen, Nguyen-Huu, Le, Huynh, Vu, David Lo, Le-Cong (HUST, Sydney, SMU, Melbourne, SUTD)
- Problem: >50% of vulnerability DB entries (NVD/GHSA) have missing/incorrect affected-library fields; existing methods treat it as text retrieval/generation.
- Method: Build security KG (CVE, CWE, CPE, library, ecosystem; 5 relations), knowledge-graph completion (SimKGC / RAA-KGC) for link prediction, then LLM re-ranking (DIFT adapted to multi-label, promote-then-fill) with graph embeddings injected.
- Data: VulLib (2,853 Java CVEs); chronological-ish split.
- Findings: +32% Avg F1 over VulLibGen; 110M KGC backbone beats 7B generative baseline; fine-tuned Gemma4 31B re-ranker beats zero-shot GPT-5.5/Claude Opus 4.7; robust to 30% edge removal; failures = new libraries, intra-family distractors.
- Line of work: continuation of Lo's affected-library identification series (Chen 2020 ICSE-SEIP, Haryono 2022 ICPC, Chronos ICSE 2023).
- Security relevance: HIGH (supply chain, SCA). RE relevance: LOW (none explicit).
- Reusable pattern: structured knowledge (graph) + LLM re-ranker; "text-only assumption is the limitation" framing; realistic temporal split caveat.

## P02 — 2026.findings-emnlp.916.pdf
- Title: Talking to Itself While Coding: What Makes Comments Help Code Generation?
- Venue: Findings of EMNLP 2026
- Authors: Pan, Sun, Zhang, David Lo, Du (Monash, SMU)
- Problem: Do self-emitted comments causally improve LLM code generation pass@1?
- Method: observational (88 models, LiveCodeBench; form + WHY/WHAT intent via LLM judge) + controlled intervention (prefill weak recipient with strong source's comment block; conditions: source-correct/wrong, shuffled, wrong-topic, random, corrupted) + self-elicitation (14 models x 10 prompt variants) + RepoClassBench replication (C#, Java).
- Findings: form/intent don't track pass@1; correct content lifts +17.2%; wrong-topic -20.8%; shuffling retains 68% of lift; prompting recovers ≤24% of the lift; same prompt helps some models and hurts others.
- Security relevance: LOW. RE relevance: MEDIUM (natural-language specification/intent as context; "content correctness not form" is a lesson for NL-to-code and for requirement-as-prompt).
- Reusable pattern: observational null → controlled causal intervention → "can prompting replace it?" structure; rigorous stats (McNemar + Holm).

## P03 — 3832254.pdf
- Title: Understanding and Improving Model Editing for Secure Code Generation
- Venue: ISSTA 2026 (PACMSE)
- Authors: Sun, Zhang, Chen, Yang, Tan, David Lo (SMU, NJUST, NJU, SYSU)
- Problem: Can model editing (localized parameter updates) harden code LLMs against insecure generation vs inference-time hardening (CoSec)?
- Method: empirical study of UltraEdit, DINM, DEFER* vs CoSec on 6 LLMs (3B–8B); SR via CodeQL on 9 seen CWEs + 29 prompts of 17 unseen CWEs; perturbation robustness; HumanEval Pass@k; then proposes SafeEdit = functional tuning + edit-aware L2 regularization anchoring edited params; CodeGuard+ and MultiPL-E validation.
- Findings: editing +15–25% SR on seen CWEs, robust to perturbations; weak/inconsistent generalization to unseen CWEs; functional regressions (DINM severe); SafeEdit restores Pass@1 (+11.7–15.5 pp over UltraEdit) with security mostly kept; complementary with CoSec; editing much cheaper than CoSec; sensitive to depth/location/suffix length.
- Security relevance: HIGH (secure code generation). RE relevance: LOW–MEDIUM (security requirements as "knowledge to inject"; trade-off between security and functional requirements).
- Reusable pattern: "empirical study + enhanced approach (RQ4)" paper template; seen/unseen split with Jaccard=0 check; security–correctness harmonic trade-off score; manual CodeQL validation (40 samples).
## P04 — 3832102.pdf
- Title: Learning from the Test: Self-Referential Differential Testing for Deep RL Agents (tool: Delta)
- Venue/year: Proc. ACM Softw. Eng. (PACMSE) Vol. 3, ISSTA 2026, Article ISSTA011, October 2026. DOI 10.1145/3832102.
- Authors (and affiliations; note whether David Lo is an author): Junda He (SMU), Jieke Shi (SMU), Zhou Yang* (University of Alberta, Canada CIFAR AI Chair / Amii; corresponding author), Mingfei Cheng (SMU), David Lo (SMU). **David Lo is an author (last author).**
- Problem: Existing DRL testing finds only safety-critical failures (crashes); it ignores *optimality bugs* (agent is safe but suboptimal, e.g. wastes energy). Optimality has no testing oracle: the true optimal policy is unknown, and training extra reference agents from scratch is prohibitively expensive.
- Method (design, data, baselines, metrics): Two-phase framework Delta. (1) Safety testing with the SOTA fuzzer CureFuzz, while logging every AUT trajectory (state, action, reward, next state) into a static dataset D. (2) Optimality testing: train a "challenger" agent from D with offline RL (BC, BCQ, CQL compared), then run energy-guided differential fuzzing (seed energy = diversity via curiosity/RND networks + regret exp(R_ca − R_aut) + inconsistency via LSH on state sequences); any initial state where the challenger's cumulative reward exceeds the AUT's (+δ, default 0) is an optimality bug. Black-box, assumes deterministic policy/environment; §6.2 adds a Mann-Whitney statistical oracle for stochastic environments. Environments: CartPole, MountainCar, Acrobot (DDQN AUTs), Hopper, Walker2D (SAC AUTs), via d3rlpy. Baselines (no direct prior work exists): MDPFuzz, CureFuzz, GMT, all given the same BCQ challenger as oracle. 2-hour budgets, 5 repetitions, 95% CIs, Mann-Whitney U + Cohen's d. Metrics: # bugs, # distinct bugs (grid-discretised initial-state space), Distance (mean pairwise Euclidean distance of bug seeds). 4 RQs: best offline RL algorithm; vs. baselines; ablation of energy components; usefulness of bugs for repair (CQL fine-tuning on challenger's superior trajectories → "AUT-Improved").
- Key findings (with concrete numbers): Challengers trained offline perform close to the AUT and train much faster than the AUT. BCQ challengers find the most bugs in all five environments (e.g. MountainCar 3752.0 vs BC 1243.2 vs CQL 2144.0); average 2,517.9 optimality issues per environment. Delta finds on average 50.2% more bugs than the best baseline (per-env +34.1% to +91.5%), and far more distinct bugs (Acrobot 467.4 vs 93.2, +401.5%; Hopper 1648.8 vs 769.2). Distance metric: best or tied in 4/5 envs; GMT wins on CartPole (0.084 vs 0.071). Ablation: removing Regret causes the largest drop in total bugs (Acrobot 5450→2238), removing Diversity halves distinct bugs on CartPole (81.0→39.4). Repair: AUT-Improved raises reward in all envs (CartPole 495.7→500±0; Walker2D 3925.5→4399.3, +12%), eliminates 100% of known safety failures on CartPole/MountainCar and 97.8% on Walker2D; CureFuzz re-fuzzing finds fewer failures (Acrobot 1183.6→265). Non-deterministic Hopper-Noise: Delta +171% vs best baseline (87.8 vs 32.4 bugs).
- Stated future work / limitations: Evaluate on more complex real-world domains (autonomous driving); try newer offline RL algorithms for stronger challengers. Limitations acknowledged: assumes deterministic AUT/env in main experiments (stochastic extension only on one env); the challenger's quality depends on the safety-testing dataset being diverse; challenger is only a local oracle; the oracle inherits the reward function R as the reference objective; threats: randomness (mitigated with 5 runs + stats), generalisability (five classic/MuJoCo tasks only), metric construct validity.
- Security relevance: LOW-MEDIUM — framed as reliability/quality of DRL systems (safety failures such as crashes and unhealthy states), not security; no adversarial or vulnerability angle beyond "safety-critical hazards".
- Requirements-engineering relevance: LOW — the only RE-adjacent point is that the reward function R is treated as the specification/objective and non-functional concerns can be encoded into R; no requirements, NL specs or acceptance criteria are involved.
- Reusable pattern: Identify an unaddressed quality dimension (optimality vs. safety) that lacks an oracle → relax the oracle via differential testing with a cheaply derived reference (reuse test-phase logs as training data) → wrap it in a fuzzing loop with a multi-factor energy function → RQ structure: component choice, vs. baselines (adapted since none exist), ablation, downstream usefulness (repair), plus discussion extensions (clustering, stochastic setting) and a replication package.

## P05 — 3832162.pdf
- Title: From Greedy Steps to Global Optimization: Learning Sequential Test Suite Generation (tool: TestDecision)
- Venue/year: Proc. ACM Softw. Eng. Vol. 3, ISSTA 2026, Article ISSTA071, October 2026. DOI 10.1145/3832162.
- Authors (and affiliations; note whether David Lo is an author): Guoqing Wang (Peking University & ISCAS), Chengran Yang* (SMU, corresponding), Xiaoxuan Zhou (Northeastern University, China), Zeyu Sun* (ISCAS, corresponding), Bo Wang (Beijing Jiaotong University), David Lo (SMU), Dan Hao (Peking University). **David Lo is an author (6th of 7).**
- Problem: Open-source LLMs (needed for cost/privacy) generate unit-test suites iteratively but suffer "structural myopia": they fail to produce new tests with high marginal coverage gain given the current suite, and coverage feedback in prompts does not help (pilot study: Qwen2.5-Coder-7B line coverage 52.34% guided vs 52.43% blind; CodeLlama drops 40.34%→38.17%). There is no theoretical account of whether sequential generation approximates the globally optimal suite.
- Method (design, data, baselines, metrics): Formalise test-suite generation as an MDP (state = checked status of program under current suite; action = generate one test); prove the suite utility is monotone submodular and the global problem NP-hard, so a step-wise greedy policy achieves ≥(1−1/e) of optimum (Nemhauser). TestDecision = (1) inference framework: at each step execute the suite with Coverage.py, inject "#uncovered" markers into the AST (in-context coverage projection) and prompt the LLM to maximise marginal gain; (2) training: GRPO reinforcement learning with reward r = Δcov(a_t)·I(Valid(a_t)) (normalised new line coverage, zeroed if the test fails to execute); SFT is argued to lack this marginal-gain signal. Training data: 70% of ULT tasks, candidate tests sampled from GPT-5-mini (N=20), greedily ordered and replayed, keep trajectories >90% coverage → 8,396 state samples. Base models: Qwen2.5-Coder-7B, Llama-3.1-8B, CodeLlama-7B (plus Qwen 3B/14B in discussion). Benchmarks: ULT held-out 30% (in-distribution) and LiveCodeBench post-June-2024 (OOD, bug detection via buggy solutions). Baselines: zero-shot base models with ULT's iterative guided pipeline, ChatTester, SymPrompt, TestCTRL (PPO), plus GPT-4o, GPT-5.2 and CODAMOSA in discussion. Metrics: syntactic correctness, execution pass rate, line/branch coverage (and Coverage@k), mutation score (Cosmic-Ray), bug-detection rate. 3 seeds, Wilcoxon signed-rank p<0.01. 4 RQs: effectiveness, sequence optimisation, generalisation/bug detection, ablation. Trained on 8×A100 with Verl, G=8, lr 1e-6, KL β=0.001, 3 s sandbox timeout.
- Key findings (with concrete numbers): On ULT, TestDecision-Qwen lifts line coverage 51.42→69.69%, branch 43.23→65.87% (+52.37% rel.), execution pass rate 16.86→67.14% (+298%), mutation score 33.80→57.13%; prompting baselines underperform even the base model (SymPrompt 34.50% line; ChatTester execution 6.14%); vs TestCTRL +61.54% line coverage. At k=1 it already reaches 58.27% line coverage (base 47.31%) and keeps growing after k=3 (2.6% vs 0.3% gain from k=3 to 5). On LiveCodeBench: line coverage 49.61→62.47%, bug detection 20.50→32.50% (TestCTRL 24.00%); CodeLlama execution rate 5.78→34.80%. Ablation (Qwen): w/o RL (SFT) 54.14% line / 23.98% execution; w/o greedy inference 63.27%; inference framework alone on frozen model 59.29%. Scaling: 3B +5.79 pts, 7B +18.27 pts, 14B reaches 74.01% line coverage (above GPT-5.2's 69.40%); 7B matches GPT-5.2 and beats GPT-4o (59.88%) and CODAMOSA (52.73%).
- Stated future work / limitations: Python only (needs dynamic instrumentation); function-level ULT vs industrial system-level testing; off-policy training data (distribution mismatch) — on-policy/iteratively refreshed collection is future work; theory does not exclude degenerate "mega-tests" — incorporate test length/complexity constraints; line coverage used as reward is a proxy for fault detection (mutation too slow at 76.53 s avg); equivalent mutants; transfer to statically typed languages by swapping coverage tools.
- Security relevance: LOW — unit-test generation for coverage and bug detection; sandboxing of generated tests is mentioned only as an engineering safeguard.
- Requirements-engineering relevance: LOW-MEDIUM — tests act as executable specifications/oracles and bug detection ties to intended behaviour, but no explicit requirements, NL specs or acceptance criteria are modelled.
- Reusable pattern: Motivate with a pilot study that quantifies a failure mode (structural myopia) → give a formal framing (MDP + submodularity proof) that justifies a simple algorithm → build inference-time scaffold + RL training with a verifiable execution-based reward → evaluate on leak-free benchmarks (in-distribution + OOD) against three baseline families (base, prompting, learning), with ablation and scaling-law discussion, and a "7B open model matches proprietary frontier model" headline.

## P06 — 3832262.pdf
- Title: E2WR: An Effective and Efficient Reduction Framework for WebAssembly Binaries
- Venue/year: Proc. ACM Softw. Eng. Vol. 3, ISSTA 2026, Article ISSTA171, October 2026. DOI 10.1145/3832262.
- Authors (and affiliations; note whether David Lo is an author): Shiyao Zhou (Hong Kong Polytechnic University), Ningyu He (HK PolyU), David Lo (SMU), Xiapu Luo (HK PolyU). **David Lo is an author (3rd of 4).** Funded by NSFC, HK RGC and HK ITF grants.
- Problem: Bug-triggering Wasm binaries (from runtime fuzzers) are unreadable and huge (avg 176,631 instructions), so they must be reduced while preserving the bug. Language-agnostic reducers (Perses, Vulcan, T-PDD) generate many invalid variants (stack imbalance) and miss Wasm semantics; Wasm-specific reducers (Wasm-Reduce, Wasm-Shrink) lack delta-debugging-style intra-function instruction reduction, and RR-Reduce only prunes whole functions. Challenges: synthesising type-correct replacements for removed instructions under changing context, avoiding redundant padding, going beyond 1-minimality, and reducing non-function definitions (globals, tables, types) efficiently.
- Method (design, data, baselines, metrics): Three techniques: (1) ODGIR, operand-dependency guided instruction reduction — builds producer/consumer operand-dependency graphs so delta debugging can remove instruction chunks and synthesise stack-type-preserving replacements only where needed; (2) CARE, combination-aware redundancy elimination — removes instruction combinations whose stack effects cancel, including ones crossing AST-node boundaries; (3) definition reduction combining static analysis with delta-debugging trials and index rewriting; plus a Wasm-Specialized Reducer (function inlining, signature shrinking, size-reducing transformations). Benchmark: new 75-binary suite (28 from Wapplique/LWDIFF/WASMaker bug reports, 19 from runtime testers such as wasm-smith, 28 from RR-Reduce's dataset), "largest benchmark for Wasm reduction". Oracle = differential behaviour between buggy and fixed runtime versions. Baselines: Wasm-Reduce, Wasm-Shrink, Perses, T-PDD, Vulcan (adapted via WAT + extended ANTLR grammar), RR-Reduce and Hybrid-Reduce in RQ3. Metrics: runtime, output bytes, instruction count, oracle invocations, reduction speed (B/s, #/s), geometric means, 5 runs, Wilcoxon rank-sum p<0.05 reported as Better/No-diff/Worse counts; 6 h time limit, 32 GB Docker memory limit. 3 RQs: vs. existing reducers, ablation, comparison/composability with RR-Reduce. Open source: github.com/erxiaozhou/E2WR.
- Key findings (with concrete numbers): E2WR geometric mean output 172 B / 19 instructions in 93 s with 512 oracle calls. Versus Wasm-Shrink: 95.0% smaller binaries, 98.4% fewer instructions, 10.1×–12.4× faster, 88.2% fewer oracle calls, significantly better on 75/75 programs (size). Versus Wasm-Reduce (57 programs it handles): 68.6% smaller, 75.2% fewer instructions, 7.9× faster; worse in only 4/57 (size) due to local optima (lacks concrete stack values). Versus Perses/T-PDD/Vulcan (which crash on 21/4/22 programs): 55.8%–94.6% smaller, 1.5×–18.3× speedups, 91.8%–99.5% fewer oracle invocations. Ablation: w/o ODGIR → 70.1% more instructions and 26% more time; w/o CARE → 9.2% more instructions at 1.5% time cost; w/o definition reduction → binary 565 B vs 172 B (significant on 71/75); w/o Wasm-Specialized Reducer → 38.7% larger, 47.4% more instructions but 8.3% faster. RQ3: RR-Reduce fails on 44/75; on the remaining 31, E2WR output is 99.4% smaller but takes 392% more time; E2WR's whole output (99 instr.) is smaller than RR-Reduce's localised target function (1,028). Pipeline E2WR+RR: 468 B vs 557 B (E2WR alone) and 40.2% smaller than Hybrid-Reduce (782 B).
- Stated future work / limitations: Random constant values in replacements can affect whether oracle accepts (mitigated by 5 runs); tracks only stack types, not concrete values, so can get trapped in local optima; ODGIR/CARE could be adapted to other stack-based bytecodes (JVM) with new graph construction and type rules; baselines fail on subsets so comparisons are over shared subsets. No explicit "future work" section beyond generality discussion.
- Security relevance: MEDIUM — motivated by Wasm runtime bugs that cause memory corruption and security breaches in blockchain/cloud/financial settings; the tool supports debugging fuzzer-found runtime bugs, but it is a reduction/debugging technique rather than a security analysis.
- Requirements-engineering relevance: LOW — pure program-reduction/debugging tooling; no requirements, specs or intent.
- Reusable pattern: Pick a language where generic tooling (delta debugging / AST reducers) breaks on language semantics → enumerate 3 concrete challenges → one technique per challenge → build the largest benchmark to date from prior studies' bug reports and fuzzers → RQs: vs. SOTA (both language-agnostic and language-specific), ablation per component, orthogonality/composability with the closest competitor; report geometric means + per-program Wilcoxon B/N/W counts; release tool.

## P07 — 2026.findings-emnlp.191.pdf
- Title: Extending Fill-In-the-Middle with Instructions for Steerable Code Completion (method: IFIM, Instruction-aware Fill-In-the-Middle)
- Venue/year: Findings of the Association for Computational Linguistics: EMNLP 2026, pages 4050–4066, October 24–29, 2026.
- Authors (and affiliations; note whether David Lo is an author): Zhensu Sun (SMU), Chengran Yang* (SMU, corresponding), Chao Peng (University of Edinburgh), Pengfei Gao (Independent Researcher), Xiaoning Du (Monash University), Li Li (Beihang University), David Lo (SMU). **David Lo is an author (last author).**
- Problem: Code-completion LLMs pre-trained with Fill-In-the-Middle (FIM) fail when developer intent is under-specified; developers add NL comments (e.g. "# filter out negative numbers") but FIM models treat them as background noise in the prefix, and open-source FIM data has few instruction-to-code pairs. Ordinary instruction tuning degrades FIM ability, and routing to a second "edit" LLM adds latency and breaks KV-cache reuse.
- Method (design, data, baselines, metrics): IFIM fine-tunes a FIM-pretrained model with a fourth, structurally separated instruction section led by an <INS> token (a repurposed rare vocabulary token to avoid re-initialising the LM head); three placements per FIM mode (IPSM, PISM, PSIM). Objective: maximise log P(M | P, S, I). At usage time, instructions are written as specially marked inline comments ("#!"), parsed by the IDE. Training data: 122.9k snippets from OSS-Instruct and evol-codealpaca (70% Python), 1–3-line middle spans, instructions synthesised with GPT-4.1 (gpt-4.1-2025-04-14), one-sentence filter, decontaminated against HumanEval/MBPP. Base models: DeepSeek-Coder-6.7B and Qwen2.5-Coder-7B (plus Qwen 1.5B/3B); baselines: base model with instruction appended as a comment, official instruct versions with a FIM prompt, and a model fine-tuned on the raw data without instructions ("finetuned"). Benchmarks: IHumanEval (312 single-line infilling samples, docstrings removed) and IRepoMasterEval (256 samples, six languages, ±20-line context), with GPT-4.1-synthesised and manually revised instructions (inter-rater agreement 0.72); plus an in-the-wild set of 100 real developer TODO/FIXME instructions mined from GitHub commits after 2025-06 (Edit Similarity + MiMo-V2.5 LLM-judge 1–5). Metric: Pass@1 (greedy, 128 tokens). Ablations: instruction position, data ratio, standalone section vs. inline comment training, noisy instructions (misspelled/lengthy/ambiguous), cross-lingual, IDE overheads (latency, diversity, edit locality), and reversed-instruction alignment with human annotation (agreement 0.69). Training: 2 epochs, Adafactor, lr 5e-5, 2×RTX A6000.
- Key findings (with concrete numbers): With instructions, average Pass@1 rises from 87.8% to 94.7% on IHumanEval and 14.7% to 20.7% on IRepoMasterEval (DeepSeek: 84.6→93.6% / 10.9→21.1% in PISM; Qwen: 91.0→95.8% / 18.4→20.3% in PSIM). Without instructions, IFIM matches or slightly exceeds the base (e.g. Qwen 76.0→76.3%), except IPSM on Qwen (60.3%). Official instruct models collapse on FIM (DeepSeek-instruct 39.4% / 2.1%). Training with instructions as plain inline comments is harmful (DeepSeek 84.6→79.0% IHE, 10.9→4.3% IRME). Gains hold at 1.5B/3B/7B (IHE 93.9/94.2/95.8% vs base 84.0/91.0/91.0%). In-the-wild: ES 49.5 vs 43.7 (DeepSeek) and 52.9 vs 45.1 (Qwen), judge 2.60 vs 2.43 and 2.79 vs 2.39. Noisy instructions: e.g. misspelled DeepSeek 82.2→91.0%. Reversed-instruction alignment 54.4%→80.9%. Overhead: 0.04% extra input tokens, diversity 1.20 vs 1.23, zero context repetition. Recommend PISM/PSIM; PSIM preserves suffix KV cache.
- Stated future work / limitations: Control baseline scoped to a 0% IFIM-ratio comparison; interplay with other alignment techniques unexplored; IRME context truncated to ±20 lines, so claims are limited to local-context completion — long-context evaluation is future work; training and benchmark instructions are synthetic (mitigated by the 100-sample real-developer set); Java/JavaScript slices gave 0% for all models (N=33, N=7). Ethics: better intent adherence could lower the barrier for generating malicious code; safety alignment for instruction-driven infilling is suggested as future work.
- Security relevance: LOW — only an ethics note that steerable completion could be misused for malware; no security evaluation.
- Requirements-engineering relevance: HIGH — the whole paper is about capturing and following developer *intent* expressed in natural language (NL-to-code at completion time), under-specification, instruction/intent alignment, and a benchmark of real developer-written intent statements (TODO/FIXME comments).
- Reusable pattern: Observe a practical gap from an earlier empirical study (unhelpful completions due to under-specified intent) → propose a minimal, backward-compatible change to an established training format (add one structured section) and show it is "free" (no regression) → synthesise training data with a frontier LLM, build instruction-augmented variants of existing benchmarks with human revision and reported agreement → add a small in-the-wild real-developer benchmark, multi-scale, noise, cross-lingual and deployment-cost ablations → release artifacts.
## P08 — J Software Evolu Process - 2026 - Lu - What Makes a Good Model Card.pdf
- Title: What Makes a Good Model Card?
- Venue/year: Journal of Software: Evolution and Process (Wiley), vol. 38, e70170, 2026 (received Apr 2026, accepted Sep 2026). DOI 10.1002/smr.70170.
- Authors (and affiliations; note whether David Lo is an author): Haochen Lu, Junxiao Han (corresponding), Yujie Huang, Song Han (Hangzhou City University); Jiakun Liu (Harbin Institute of Technology); Lingfeng Bao, Shuiguang Deng (Zhejiang University); **David Lo (Singapore Management University) — yes, 7th of 8 authors.**
- Problem: Hugging Face model cards are the main communication bridge between model developers and users, but prior work studied documentation practices and auto-generation without defining what a *high-quality* model card is (from the user perspective), whether quality can be detected automatically, which features drive it, and whether quality matters for model longevity.
- Method (design, data, baselines, metrics): Mixed-methods MSR + survey + classifier study, 4 RQs. Data: 624,570 HF models (Apr 2024) filtered to 304,624 with model cards; random sample (95% CI, 3.5% MoE) of 765, cleaned to 758. RQ1: closed coding of section headings into 7 categories adapted from the Prana et al. README framework (What/Why/How/When/Who/References/Other; Cohen's kappa 0.77 -> 0.92), thematic analysis into content themes (Table 2), survey of 61 HF practitioners in 19 countries + user study with 10 AI experts rating theme importance (ICC consistency p<0.001); high-quality card := contains "Model Overview" + "Model Evaluation" (What) + "Model Usage Guide" (How). Only 54/758 (7%) qualify. RQ2: 15 features in 3 dimensions (Documentation, Model Card Update, Model Meta Info), 13 classifiers (LR, KNN, DT, SVM, GB, NB, NN, XGBoost, RF, BERT, BERT+TextCNN, BERT+TextRNN, zero-shot GPT-5), stratified 10-fold CV; metrics Accuracy/Precision/Recall/F1/PR-AUC/ROC-AUC; Wilcoxon signed-rank + Cliff's delta between classifiers. RQ3: correlation + redundancy analysis, RF feature importance, Mann-Whitney + Cliff's delta. RQ4: Kaplan-Meier survival analysis (time to last update) with log-rank test, plus qualitative coding of 3 open-ended survey questions.
- Key findings (with concrete numbers): "What" and "How" are the most frequent categories; only 3 themes get expert rating >4/5 (Usage Guide 5.0, Overview 4.86, Evaluation 4.29). RF best: 94.59% accuracy, 94.57% ROC-AUC, F1 64.99% (XGBoost 93.31% ROC-AUC; GPT-5 zero-shot 82.20% ROC-AUC, 40.65% PR-AUC); RF significantly better than LR/KNN/NB only. Top-5 determinants: num-word (Cliff's d 0.719, large), num-table (0.440), num-link (0.736), num-code-block (0.772), update-interval (-0.312, negative). Models with high-quality cards survive significantly longer (log-rank p<0.05; 20% of high-quality models active >82 days vs >20 days for low-quality). Survey: benefits = ease of use (29 mentions), understanding (13); harms = users not using the model (15), unclear usage (14); strategies = automated tools (12), templates (11).
- Stated future work / limitations: 758 cards is small and heavily imbalanced (54 positives); classifier relies on structural/surface features (word count, tables) rather than semantic accuracy; definition of quality from a survey and user study (construct threat). Future: use LLMs for direct semantic quality/completeness assessment and build actionable tools to automatically improve model-card quality.
- Security relevance (HIGH/MEDIUM/LOW + one line why): LOW — documentation quality on HF; only tangentially touches misuse risk from undocumented limitations/biases.
- Requirements-engineering relevance (HIGH/MEDIUM/LOW + one line why; RE = requirements, specifications, intent, NL-to-code, acceptance criteria, compliance, policy, prioritization etc.): MEDIUM — defines quality criteria/checklist for an artifact that documents intended use, limitations and evaluation (a specification of an ML component) and recommends platform templates/required fields; method transfers directly to "what makes a good requirement/spec" studies.
- Reusable pattern (the paper's methodological template / "how David Lo's group structures a paper", 1–3 lines): "What makes a good X?" template: (1) sample artifacts from a platform via API with statistically justified random sampling, (2) closed coding + thematic analysis with kappa, (3) practitioner survey + expert user study to derive an operational quality definition, (4) train many classical/DL/LLM classifiers under k-fold CV with ROC-AUC, (5) feature-importance/determinants with effect sizes, (6) link quality to an outcome (survival analysis), (7) implications per stakeholder (developers/users/researchers/platform) + threats + replication package.

## P09 — 3832783.3837522.pdf
- Title: Demystifying Solana Bots: From GitHub Blueprints to On-Chain Fingerprints
